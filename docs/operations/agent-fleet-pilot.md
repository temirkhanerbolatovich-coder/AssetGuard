# Fleet test AssetGuard Agent

> **Сверено 2026-10-06.** Текущий статус и границы проверки: [checklist](../product/current-project-checklist.md), [аудит](../quality/project-audit-2026-10-06.md). Датированные результаты отдельных этапов сохранены с исходными датами.

Цель: на 3–5 реальных Windows-PC доказать, что Agent переживает перезагрузку, потерю сети, остановку службы и перевыпуск credential без ручного редактирования реестра и не теряет историю инвентаризации.

## Текущее основание

На 6 октября 0.1.8 — неподписанный candidate (SHA-256 `BCD24D903FDB7C03EACB51E38F3BE653938DD905B0683F360A0BC8B412D3F50F`). Один реальный PC и controlled offline/lost-ACK lab подтверждены [протоколом](../../outputs/assetguard-agent-reliability-2026-10-05.md); финальная повторная установка readiness patch на этом PC ранее отменена UAC. Полных 3–5-PC наборов нет. Исторические transport checks двух PC на 1.19/1.20 не заменяют этот fleet test.

## Правила пилота

- Для каждого PC создавать отдельный login/secret в разделе «Подключить Agent».
- Secret не записывать в протокол, таблицу, скриншот или чат.
- Все отчёты `test-assetguard-agent-readiness.ps1` сравнивать по `computer_name` и `agent_username`; login должен быть уникальным.
- На этапе pilot допустим неподписанный EXE только при ручной передаче ограниченной группе. Массовое распространение ждёт code-signing сертификат.

## Порядок для каждого PC

1. Записать модель PC, версию Windows и имя ответственного. Создать уникальный credential.
2. Сверить SHA-256 installer. Установить Agent от имени администратора и выполнить первую инвентаризацию.
3. Запустить:

   ```powershell
   .\test-assetguard-agent-readiness.ps1 -Phase INITIAL
   ```

   Отчёт должен завершиться `Passed=True`. В панели должны быть видны Agent `1.20` для новой установки либо поддерживаемый `1.19`, installer `0.1.8` и статус `ONLINE`.
4. Перезагрузить Windows, дождаться новых `COLLECTED`/`DELIVERED` и запустить фазу `AFTER_REBOOT`. Сверить новое `windows_last_boot`. Для 0.1.8 daemon должен быть Stopped/Disabled, SYSTEM delivery task — включён.
5. Отключить сеть минимум на 15 минут: в 0.1.8 должны накопиться несколько разных файлов `pending` и событий `COLLECTED`. Не публикуя XML, сохранить `OFFLINE`, затем восстановить сеть. Проверить FIFO-доставку всей очереди, максимум три за цикл, рост raw/snapshot history и опустошение pending. После нового `received_at` сохранить `NETWORK_RESTORED`. Повтор исходных байтов не должен создавать дубли raw inventory.
6. Для 0.1.8 отключить/остановить **только** `AssetGuard inventory delivery`, затем включить/запустить задание без изменения реестра; сохранить исторически названную фазу `SERVICE_RECOVERED`. Старые версии проверяются остановкой/запуском `glpi-agent`. Нельзя включать native daemon одновременно с delivery task.
7. Отозвать credential в панели и убедиться, что новая отправка получает `401`. Повторно запустить installer в режиме «Восстановить после переустановки Windows». Дождаться запроса в панели, сверить имя компьютера и SMBIOS UUID, одобрить его и сохранить `REENROLLED` после новой отправки. Ручное редактирование реестра не допускается.
8. На обесточенном PC изменить RAM или диск, загрузить Windows и дождаться отправки. Сохранить `HARDWARE_CHANGED` и проверить, что инцидент ссылается на прежний endpoint/asset и показывает фактическую разницу.

Дополнительно на каждом PC проверить ручной update с 0.1.6/0.1.7 на 0.1.8 без нового ключа/endpoint и сохранность очереди. Автоматического rollback нет: отдельно выполнить согласованный сценарий возврата и проверить единственный uploader. Controlled lost ACK сначала проверять в изолированном lab; не публиковать XML и не отключать сетевой доступ чужих рабочих ПК.

## Критерий приёмки

Тест закрыт только когда:

- есть 3–5 полных наборов отчётов с уникальными `agent_username`;
- все фазы, где система должна быть здорова, имеют `passed=true`;
- после reboot, network restore, service recovery и re-enrolment появились новые immutable RawInventory и не изменился endpoint;
- ни на одном PC не пришлось вручную менять `HKLM\SOFTWARE\GLPI-Agent`;
- изменение RAM/диска дало один объяснимый инцидент без потери предыдущей истории.

При re-enrolment проверяется именно прежний SMBIOS UUID. Одобрение отзывает предыдущий активный credential этого endpoint, выдаёт новый и сохраняет прежнюю историю. Запрос действует 30 минут; неизвестное устройство нельзя одобрить, а claim token не заносится в протокол теста.
