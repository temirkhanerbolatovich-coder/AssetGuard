# Реестр и единый центр инцидентов

Этап UI/UX 2, 2026-10-05. Реализация на текущем FastAPI/PostgreSQL и browser frontend; миграция БД и новая UI-зависимость не требуются. Статус публикации фиксируется в [checklist](../product/current-project-checklist.md).

## Работа сотрудника

Обзор сначала показывает до шести задач: активные инциденты по приоритету и времени, затем компьютеры с проблемами или без данных Agent. Каждая задача содержит источник, время и переход к карточке. Открытые инциденты включают технические события и физические расхождения. Счётчики имущества и компьютеров различаются: непривязанный Agent не становится дополнительной позицией имущества.

Реестр показывает название, тип, инвентарный номер, кабинет, состояние, количество/единицу и способ проверки. Поиск, категория, состояние, кабинет, наличие изменений и сортировка работают совместно; список рисует по 20 записей. Кабинет выбирается по UUID, поэтому одноимённые кабинеты разных корпусов не смешиваются. Выбранные фильтры видны над списком и явно сбрасываются. Из карточки сохраняются фильтры, сортировка, страница и позиция прокрутки реестра в текущей сессии браузера. Reload и новый вход начинают список заново; сохранённые представления/URL-фильтры пока не реализованы.

Мебель, принтер и другое имущество без endpoint имеют состояние «Ручной учёт», а не ложный offline. Компьютер без endpoint/снимка показывает отсутствие данных Agent; списанная позиция — «Списан». Количество и единица видны также в карточке. Технические вкладки доступны при наличии endpoint; учётная история остаётся доступной для физического имущества.

Центр инцидентов объединяет Agent и физический обход. Фильтры: поиск, статус, приоритет, источник, кабинет и даты; по умолчанию открытые/на проверке. Даты относятся к местному времени браузера и включают обе границы. Начало после конца показывает ошибку и не возвращает вводящий в заблуждение список. На телефоне дополнительные фильтры раскрываются по кнопке. Карточки и pagination ограничены 20 записями на странице.

Физическая карточка открывается по `#physical-incident=UUID`: исходный обход, ожидаемое/проблемное количество, результат, проверяющий, время, комментарий и неизменяемая история решений. Операция использует существующий room workspace, dialog и API, включая контроль количества и PDF-акт. Кнопка блокируется на время отправки и повторный submit в этот период игнорируется; это защита UI, а не новая гарантия идемпотентности произвольного API-клиента. После решения карточка обновляется. Старые `#room`, `#incident`, `#asset` и Telegram-ссылки совместимы.

## Контракт чтения и доступ

- `GET /admin/locations/physical-incidents` — список кратких записей: идентификаторы инцидента/актива/кабинета, название и инвентарный номер, тип расхождения, затронутое количество, status/severity/title/created_at. Evidence и решения в список не копируются.
- `GET /admin/locations/physical-incidents/{incident_id}` — существующее представление физического инцидента и решений, `room_path`, `evidence`: inspection_id/completed_at/inspector_name/expected_quantity/affected_quantity/result/comment.

Оба маршрута требуют `require_viewer`. Scoped ADMIN ограничен организацией; остальные роли дополнительно ограничены разрешёнными кабинетами. Фильтрация по организации применяется отдельно от room grant: ошибочный grant чужой школы не открывает её данные. Проверяется исходный кабинет инцидента, чтобы перемещение актива не меняло доступ к первоначальному доказательству. Несуществующий или недоступный инцидент возвращает 404, отсутствие авторизации — 401, некорректный UUID — 422. Право читать не даёт права изменять: решения используют прежнюю authorization policy. Полная [матрица](../security/admin-route-access-matrix.md) содержит 62 защищённые операции.

## Ошибки и проверка

Чтение использует общий timeout, session/view generation и отмену запросов каркаса. Ошибка карточки показывает retry; поздний ответ после смены раздела/выхода не рисует прежние данные. Сбой общего списка не представляется пустым успешным результатом. Выход очищает также фильтры, страницы и DOM инцидентов.

Проверки из `backend`:

```powershell
$env:ASSETGUARD_RUN_BROWSER_E2E='1'
.\.venv\Scripts\python.exe -m pytest -q tests/unit tests/integration tests/e2e
```

`test_physical_incident_reads.py` проверяет две организации, неназначенный кабинет, ошибочный foreign grant, VIEWER/ADMIN и неизменяемые evidence. Route-contract tests проверяют все 62 операции. Browser E2E создаёт 44 групповые позиции в двух кабинетах с одинаковым номером, принтер и компьютер Agent; проверяет совместные фильтры/сортировку/pagination, возврат, оба типа инцидентов, прямую ссылку после reload, частичное списание, единственное решение и PDF-акт. Узкие экраны проверяются на 320/390/768/1366 px. Preview с синтетическими данными можно получить через `ASSETGUARD_CAPTURE_UI_PREVIEWS=1`; это не фотографии production-данных.

Из корня также выполняются `node --check frontend/app.js` и `git diff --check`.

## Ограничения

Pagination пока ограничивает DOM, но API списков загружает все доступные записи, как существующий реестр. Производительность на 1000+ позициях не измерена; серверная pagination и сохранённые URL-фильтры требуют отдельного согласованного контракта при расширении пилота. Полная WCAG/zoom/performance/usability приёмка остаётся этапом 5. Agent stale/fleet readiness, installer и ограничения production Vision сохраняются самостоятельными задачами. Исходное ТЗ, модель/inference/storage Vision и правила baseline не изменены.
