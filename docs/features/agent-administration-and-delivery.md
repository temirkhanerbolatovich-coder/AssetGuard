# Agent, сотрудники и доставка уведомлений

UI/UX этап 4, 2026-10-05. Существующий frontend и HTTP authorization расширены без нового framework, зависимостей и миграции. Модель и обработка Vision не менялись.

## Работа администратора

Из технического состояния обзора откройте «Компьютеры Agent и доставка». Администрирование разделено на четыре рабочие вкладки: компьютеры, подключение/ключи, восстановление и Telegram. На экране показывается только выбранная задача. Стрелки влево/вправо, Home и End переключают вкладки с переносом клавиатурного фокуса. Сотрудники, импорт/экспорт и справка Agent остаются отдельными переходами рядом с вкладками.

Список компьютеров использует уже разрешённый `/admin/endpoints`. Поиск — имя, название имущества и инвентарный номер; фильтр — состояние; страницы по 20 записей. Показываются последняя связь, состав, причина проверки и ссылка на связанную карточку. `STALE` определяется по последней связи и серверному `agents.stale_after_hours` из `/admin/operations/status`, с сохранением приоритета `IDENTITY_CONFLICT` и `OFFLINE`. Чтение не запускает maintenance и не меняет сохранённый статус. Это отсутствие свежих данных, а не доказательство пропажи. Привязка ключа означает привязку к endpoint и не означает ONLINE.

Если компьютеров ещё нет, экран ведёт сразу к подключению первого Agent. Пустой результат поиска предлагает сбросить фильтры. Очередь Telegram различает действительно пустую очередь и пустой результат выбранного состояния; во втором случае можно одним действием показать все записи. Загрузка очереди не выглядит как успешная пустая выдача.

Ключ создаётся существующим API. Логин/секрет показываются один раз, только после успешного создания, до обновления списков. Копирование сообщает результат; при закрытии, Escape и выходе поля очищаются. Списки, очередь и логи не получают секрет. Инструкция честно отмечает 0.1.8 как пилотный кандидат: публикация подписанного релиза и fleet acceptance ещё не завершены.

Запрос восстановления показывает компьютер, аппаратный идентификатор, установщик и срок действия. Истёкший запрос не имеет кнопок решения. Подтверждение называет объект и предупреждает об отзыве прежнего ключа; отклонение и отзыв ключа также называют объект. API заново проверяет роль, tenant и актуальный статус; локальное истечение может иметь погрешность часов браузера.

В «Сотрудники и доступ» видны учётные записи, роли, активность и назначения. Новые назначения предлагают активных сотрудников без ADMIN; выбранные школа/область сохраняются при обновлении, если доступны. Ошибки создания пользователя, назначения и ключа появляются в форме, сохраняют поля и получают фокус. Повторный submit блокируется до ответа. Общий диалог подтверждения блокирует повтор, отмену и Escape во время записи и не применяет ответ к новой сессии. Ошибка возвращает возможность повторить действие. Изменение роли/пароля/активности существующего сотрудника остаётся API-функцией; новый редактор аккаунта в этот этап не входит.

## Чтение доставки

`GET /admin/notifications?status=RETRYING&limit=20&offset=0` допускает только ADMIN. Администратор школы видит свою организацию; legacy bootstrap администратор платформы — все. Остальные роли и анонимный запрос получают существующий отказ `401`. Доступность меню не заменяет серверную проверку.

Параметры: `status` отсутствует либо `PENDING`, `RETRYING`, `SENT`; limit 1–100, offset 0–10000, неверный ввод — 422. Порядок: created_at DESC, id DESC. Ответ содержит summary (pending/retrying/sent), total для выбранного фильтра, limit/offset и items. В items только id, вычисленное состояние, attempts, created_at, next_attempt_at, sent_at, безопасный last_error_code и проверенная внутренняя route. Разрешены только `#incident=UUID`, `#physical-incident=UUID`, `#room=UUID`; неверная ссылка отсутствует. Неизвестные коды ошибки заменяются `UNKNOWN_ERROR`. Payload, текст, event key, получатель, Telegram message id и bot token не возвращаются.

- PENDING: ожидает первой попытки (attempts=0).
- RETRYING: запись всё ещё PENDING, но попытка уже была; показывается время следующей.
- SENT: принято Telegram, без подтверждения прочтения человеком; next_attempt_at отсутствует.

Summary считает все разрешённые записи независимо от фильтра. `operations.notifications.pending` сохраняет прежнее значение: все ожидающие, включая retrying. UI отдельно объясняет отличие. Сводки — текущие чтения, не атомарный снимок одновременно с работой worker. Панель загружается по открытию раздела и вручную, без фонового polling. Ошибка убирает недостоверный список и предлагает повтор; поздний ответ старого запроса/сессии игнорируется. Чтение не отправляет сообщения и не меняет очередь. Ошибки повторов входят в состояние внимания на обзоре.

Это очередь событий имущества. Серверный monitor отдельно отправляет состояние сервера и агрегаты Agent; его fingerprint/дедупликация не хранятся в этой таблице. Кнопок принудительной отправки/повтора нет. Не менялись at-least-once доставка, tenant routing worker и ограничения retention, описанные в [Telegram](telegram-notifications.md).

## Проверка и ограничения

Из backend: `python -m pytest tests/integration/test_notification_reads.py tests/unit/test_health.py tests/unit/test_admin_route_contract.py -q`. Из root: `node --check frontend/app.js`, `git diff --check`. Browser: `ASSETGUARD_RUN_BROWSER_E2E=1 python -m pytest tests/e2e/test_dashboard.py -q` из backend. Сценарий проверяет вкладки и клавиатуру, страницы/STALE, очередь/503/retry, секрет/копирование/Escape, двойной submit, известный PC/re-enrolment с отзывом старого ключа и сохранение полей после 409. Для локальных синтетических снимков задайте каталог в `ASSETGUARD_REDESIGN_PREVIEW_DIR`.

Tenant/security тесты проверяют собственные, чужие и unassigned записи, платформенную область, роли, пагинацию, фильтр, безопасные ссылки, отсутствие payload и секретов. Production browser acceptance использует только чтение; записи проверяются в изолированной БД, без запуска Telegram worker.

Пагинация Agent ограничивает DOM; список endpoints пока загружается целиком. Полная WCAG/zoom/performance/usability проверка — этап 5. Формы сохраняют ввод после подтверждённого отказа; при потере ответа записи сначала нужно обновить состояние. Защита повторного нажатия не является API exactly-once. Ручная fleet-проверка 3–5 ПК, подпись/публикация установщика, retention очереди и индивидуальные переходы Agent остаются отдельными задачами.
