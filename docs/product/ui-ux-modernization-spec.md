# AssetGuard: ТЗ на модернизацию UI/UX

Версия 1.1, 2026-10-05. Статус: направление принято; первый этап внедрён, этапы 2–5 запланированы. Это отдельное дополнение к продуктовым требованиям; исходное ТЗ и логика Vision не заменяются.

## Цель и границы

Сотрудник школы должен быстро понять, что требует внимания, найти имущество, провести обход и принять ответственное решение. Внешний вид должен поддерживать эти задачи: спокойный рабочий интерфейс, ясная иерархия, читаемые таблицы и предсказуемые действия.

Сохраняем FastAPI/PostgreSQL и существующий browser frontend, роли, location scope, доказательства, explicit baseline и append-only history. Новый framework не является условием редизайна. Backend меняется только там, где новый сценарий требует отсутствующего контракта, с соответствующими authorization tests. Автоматическое признание кражи, автопринятие baseline и переписывание Vision не входят в работу.

## Текущая точка: что проверено

Проверены текущие routes, исходники frontend и открытый production экран до входа. У приложения уже есть отдельный импорт/экспорт с preview/apply, управляемые dialogs, карточки активов/кабинетов, роли и мобильная навигация. Исторический audit от сентября не является списком актуальных дефектов.

Обнаружены основания для следующих изменений:

- На публичном экране форма входа встроена в левую панель, а основная область показывает загружаемые placeholders до авторизации. Пользователь не понимает, ожидать данные или входить.
- «Устройства» объединяет компьютеры и прочее имущество. Название и представление должны объяснять различие актива, endpoint и Agent.
- Глобальный раздел инцидентов показывает технические события; физические расхождения доступны в кабинете. Для единого рабочего списка понадобится защищённый API чтения физических инцидентов.
- Агрегаты Agent полезны, но не заменяют список конкретных ПК с причиной и временем последней связи.
- Типографика и плотность неоднородны; предлагаем общие tokens и единые компоненты.

Контраст всех сочетаний, доступность всех authenticated экранов, реальная скорость работы сотрудников и usability ещё не измерены. Они входят в приёмку; их нельзя считать уже пройденными по внешнему виду.

## Пользователи и задачи

| Роль | Основные задачи | Как проверяем результат |
| --- | --- | --- |
| IT-сотрудник в пределах существующих полномочий | Найти проблемный Agent; изучить изменение оборудования; зафиксировать решение | Из overview до причины проблемы не более двух переходов; прежний фильтр сохраняется |
| INVENTORY_CLERK / LOCATION_MANAGER | Найти имущество; провести разрешённые операции в назначенной области | Пользователь проходит полный разрешённый сценарий с проверкой количества, кабинета и результата сохранения |
| ADMIN | Настроить пользователей/доступы и Agent credentials | Точное описание области доступа; повторная проверка backend authorization |
| VIEWER | Найти актив/кабинет, прочитать состояние и историю | Доступные данные читаются; запрещённые действия не предлагаются и отклоняются API |

Существующие роли: ADMIN, VIEWER, LOCATION_MANAGER и INVENTORY_CLERK. Профессия IT-сотрудника не является новой ролью. Права операций сверяются с текущими API dependencies и grants; расширение полномочий не входит в косметический редизайн.

## Навигация и общий каркас

Основная навигация: **Обзор → Реестр имущества → Инциденты → Кабинеты → Импорт и экспорт**. Vision сохраняется отдельным экспериментальным разделом с честным состоянием доступности. Администрирование объединяет пользователей/доступы, Agent credentials и подключение/восстановление Agent; доступность пунктов определяется ролью.

Постоянный верхний контекст: организация, текущий раздел, пользователь и выход. Локация задаётся фильтром/в карточке; смена контекста обновляет данные и исключает показ устаревшего tenant. На телефоне меню открывается явной кнопкой и закрывается после выбора раздела. URL карточек, browser back/forward и старые ссылки Telegram/QR сохраняются либо получают совместимый переход.

## Требования к экранам

P0 — первый этап, P1 — следующие функциональные этапы, P2 — после стабилизации.

| ID | Приоритет | Требование | Приёмка |
| --- | --- | --- | --- |
| UX-01 | P0 | Отдельный понятный вход; пользователь/пароль основной путь, bootstrap key — отдельный административный вариант | До входа нет бесконечной загрузки закрытых данных; ошибка понятна; после входа сохраняется исходная ссылка |
| UX-02 | P0 | Единый каркас и типографика | Каждая страница имеет заголовок, контекст и одно главное действие; mobile menu/выход/назад работают |
| UX-03 | P0 | Явные состояния запроса | Loading завершается success/empty/error/forbidden; retry доступен; смена раздела не рисует ответ прежнего запроса |
| UX-04 | P1 | Обзор задач вместо набора одинаково важных KPI | Верхний список показывает требующие внимания инциденты/Agent, источник и свежесть; каждый счётчик ведёт к соответствующему списку |
| UX-05 | P1 | Реестр имущества с типом, номером, названием, кабинетом, состоянием, количеством/единицей | Поиск + фильтры + сортировка + pagination работают совместно; чистка фильтров явная; карточка возвращает к прежнему списку |
| UX-06 | P1 | Карточка имущества: сводка, учёт, технические данные при наличии endpoint, история | Неприменимые поля не показывают ложный «offline» для мебели; перемещение/списание сохраняет контроль количества и акт |
| UX-07 | P1 | Единый центр технических и физических инцидентов | Тип и приоритет видны; фильтры status/type/room/date; доступ ограничен tenant и кабинетами; физический инцидент открывает evidence |
| UX-08 | P1 | Карточка инцидента объясняет событие | Было/стало, время, source evidence, связь с активом/кабинетом и допустимое решение; повторный submit не создаёт второе решение |
| UX-09 | P1 | Кабинет как рабочее место обхода | Список ожидаемого имущества и количества, быстрый ввод результата, итог перед сохранением; история доступна после обхода |
| UX-10 | P1 | Импорт: файл → preview → исправления → apply → итог | Ошибки привязаны к строкам, разрешённый scope виден; нет silent partial success; повторная загрузка не дублирует применённые строки |
| UX-11 | P1 | Agent: состояние и действия в одном контексте | Последняя связь и порог устаревания видны; re-enrolment approve/reject, revoke и копирование показывают результат/ошибку |
| UX-12 | P2 | Панель доставки уведомлений | Pending/retry/SENT объяснены; SENT означает Telegram acceptance; секреты бота не возвращаются браузеру; доступ к деталям ограничен |
| UX-13 | P1 | Безопасные forms/dialogs | Поля с labels, значения сохраняются при ошибке, опасное действие описывает объект/количество; focus возвращается инициатору |
| UX-14 | P1 | Единая терминология | Актив ≠ endpoint ≠ Agent; stale = давно нет свежих данных, не доказательство пропажи; UI не делает выводов сильнее evidence |

Массовые действия и сохранённые пользовательские views добавляются только при подтверждённой необходимости. Для отсутствующих API UX-07/12 сначала описываются контракт и отрицательные tests; mock data не выдаются за работающую функцию.

## Визуальное направление

Сохраняем узнаваемый teal AssetGuard. Светлая рабочая поверхность, спокойная навигация, тонкие разделители, ограниченное использование карточек, статусный цвет только по смыслу. Предварительные tokens: фон `#F6F8FA`, поверхность `#FFFFFF`, основной текст `#172B3A`, вторичный `#526272`, основной teal `#0B766E`, border `#D6DEE6`. Финальные комбинации утверждаются после измерения контраста; это не готовый сертификат доступности.

Основной текст 14–16 px, заголовок страницы 24–28 px, line-height 1.4–1.5. Сетка отступов 4/8/12/16/24/32 px; radius 8–12 px. Системный шрифт сохраняет быструю загрузку. Строка таблицы 48 px, двухстрочная 64 px; compact режим — только при сохранении удобства чтения. Основные touch controls не меньше 44×44 px. Иконка дополняет понятную подпись, а не заменяет единственный способ понять действие.

У реестра единый toolbar: поиск, фильтры, выбранные chips, сброс, главное действие, экспорт. Открытие карточки — явная ссылка в названии; checkbox/меню действий не запускают навигацию строки. Сортируемые заголовки сообщают текущий порядок. Количество всегда вместе с единицей, даты — единый часовой пояс с обозначением.

На узком экране список получает компактное представление с названием, номером, кабинетом и состоянием; дополнительные сведения доступны в карточке. Настоящие двумерные таблицы могут прокручиваться внутри обозначенного контейнера, не растягивая всю страницу.

## Доступность, адаптивность и производительность

- Проверка viewport 320, 360, 390, 768, 1024, 1366 и 1920 CSS px; 200%/400% zoom. Нет потери основных действий и горизонтального scroll всей страницы при 320 px; исключение только локальные двумерные таблицы.
- Цель WCAG 2.2 AA: текстовый контраст 4.5:1, крупный текст 3:1; значимые controls/границы 3:1; статус объясняется текстом, а не только цветом. Значения проверяются инструментом, а не на глаз.
- Клавиатура проходит весь сценарий: Tab/Shift+Tab, Enter/Space, Escape. Focus видим и не перекрыт; собственный критерий focus ring ≥2 px. Не называем более строгий AAA Focus Appearance обязательным AA критерием.
- Semantic headings, table headers, labels и доступные имена кнопок; error summary переводит focus и связывает сообщения с полями; success/retry используют умеренные live announcements.
- Запросы имеют bounded timeout и завершённое error состояние; повторное сохранение блокируется на время запроса. После сохранения виден новый результат, а не только toast.
- Целевые performance budgets, ещё не измеренные: LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 в репрезентативных замерах; отдельно журналировать cold/warm load, устройство, сеть и dataset. Проверить реестр на 216 текущих и 1000 synthetic test assets без production insert; при превышении выбрать pagination/ограниченную отрисовку по данным измерений.

## Этапы реализации и выходные критерии

2026-10-05: первый этап реализован и принят на production (`d8f6a63`, 96 backend + 6 browser E2E, CI success; [приёмка](../../outputs/assetguard-ui-stage1-2026-10-05.md)) — отдельный вход, подтверждение сессии, каркас, error/retry, отмена результатов прежней сессии и защита карточек от позднего ответа. [Поведение и проверка](../features/frontend-shell-and-auth.md). UX-13 закрыт для формы входа; модернизация остальных forms/dialogs продолжится на следующих этапах. Полная accessibility/usability приёмка пока не выполнена.

1. **Каркас, вход и состояния (UX-01/02/03/13).** Сначала небольшой browser preview на текущем stack, затем работающий вертикальный сценарий login → обзор → карточка → logout. Desktop/mobile/keyboard E2E; старые QR/Telegram ссылки открываются после входа. Выход: нет бесконечных placeholders и неоднозначного входа.
2. **Реестр, карточки и центр инцидентов (UX-04…08/14).** Единые list/table/filter компоненты, разделение типов имущества, защищённое чтение физических инцидентов. Выход: найти актив, изучить оба вида инцидентов, сохранить решение и вернуться к списку; tenant/location negative tests.
3. **Кабинеты, обход и импорт (UX-09/10).** Последовательный mobile workflow, quantity/error review и итог сохранения. Выход: полный обход и import preview/apply без потери данных; реальные ошибки разобраны по строкам.
4. **Agent и администрирование (UX-11/12).** Конкретные проблемные ПК, re-enrolment/credentials, users/grants, прозрачные агрегаты доставки. Выход: разрешённые действия работают, запрещённые отклоняются API; секреты не попадают в DOM/logs.
5. **Приёмка и полировка.** Проверка keyboard, contrast, zoom, mobile и performance; модерируемый тест с 3–5 представителями ролей. Цель: ≥90% основных задач без подсказок, фиксация ошибок/времени/наблюдений. Это будущий критерий, а не уже достигнутый результат. Найденные препятствия закрываются до расширенного rollout.

Каждый этап включает работающие buttons/links/forms, негативные сценарии API, релевантные tests, обновление документации и review. Визуальный mockup без рабочей функции не закрывает этап. Fleet acceptance на реальных ПК и ограничения Vision production остаются самостоятельными задачами проекта.

## Минимальная матрица приёмки

Сценарии: вход по прямой ссылке; поиск/сортировка/фильтры и browser back; технический/физический инцидент; mobile обход; перемещение/частичное списание; Excel/PDF preview/apply; revoke/re-enrolment; read-only/forbidden; network timeout/retry; пустые списки; клавиатура и масштаб. Проверять с отдельными пользователями каждой существующей роли и с двумя tenant в тестовой БД.
