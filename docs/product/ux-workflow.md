# UX-сценарии AssetGuard

Дата: 2026-09-25. Документ фиксирует целевой пользовательский путь и границы текущей реализации.

## Для кого продукт

- **Администратор школы** настраивает структуру, ведёт реестр, импортирует ведомости, подключает Agent и назначает доступы.
- **Ответственный за инвентаризацию** работает только с назначенными помещениями и записями имущества.
- **IT-специалист** следит за компьютерами, связью Agent и подтверждёнными изменениями.

Интерфейс должен различать три сущности: **имущество** — запись школьного учёта; **компьютер Agent** — источник технического отчёта; **Agent** — установленный на компьютере сборщик. Мебель и спортинвентарь не должны выглядеть как компьютеры, от которых просто не пришёл отчёт.

## Основной путь настройки школы

1. Администратор входит и видит быстрый старт: создать кабинеты, добавить имущество, при необходимости подключить компьютеры.
2. Создаёт корпус, этаж и кабинеты. Для кабинета при необходимости указывает ответственного.
3. Загружает Excel/PDF или добавляет записи вручную. До применения просматривает все позиции по 25 строк на странице, ищет их, видит локацию и действие create/update, исключает лишние строки. Для OCR обязательно сверяет распознанные поля.
4. Если нужны технические проверки, устанавливает Agent. Найденные, но ещё не связанные компьютеры отображаются в реестре отдельно.
5. Связывает компьютер Agent только с соответствующей IT-записью школьного учёта.
6. После проверки первого отчёта человек явно подтверждает эталон. Система не должна автоматически объявлять первое наблюдение эталоном.
7. Назначает сотрудникам роли, помещения и права. После создания сотрудника интерфейс переводит администратора к назначению кабинета.

## Ежедневная проверка

1. Ответственный открывает назначенный кабинет и видит его имущество, последние данные и элементы, требующие внимания.
2. Открывает карточку нужной записи. Если это компьютер без отчёта, карточка объясняет, что проверить; если мебель или спортинвентарь — не показывает технические секции Agent.
3. При техническом расхождении IT-специалист видит сравнение «Было → Стало», время и историю. Изменение остаётся предметом проверки человека, а не автоматическим выводом о краже.
4. Результат решения попадает в историю, обращение и отчёт.

## Пустые состояния и ошибки

- Пустой реестр администратора предлагает импортировать ведомость или добавить первую запись.
- Пустой список у сотрудника говорит проверить назначение кабинета у администратора.
- Отсутствующий отчёт Agent объясняет возможную причину и следующий шаг.
- Отсутствующие системные характеристики не маскируются пустым блоком и не выдаются за нулевые значения.
- Импорт показывает полный построчный предпросмотр, число новых/обновляемых и действие для каждой строки; до подтверждения запись не выполняется.

## Что уже сделано в UX-проходе

- Добавлен быстрый старт для администратора.
- На планшете и телефоне навигация заменяется раскрываемым меню.
- Редкие действия импорта/экспорта сгруппированы; фильтры реестра можно свернуть.
- Добавлен полный предпросмотр импорта с поиском, постраничной навигацией, оценкой OCR, переключением строк и отдельным подтверждением.
- Ручной учёт имущества отделён от состояния связи Agent.
- Карточка компьютера объясняет, если он ещё не связан или не прислал отчёт; для некомпьютерного имущества технические панели скрыты.
- Создание этажа и кабинета заменено браузерными запросами на обычную форму-диалог.
- Форма имущества использует кабинет из структуры школы и один выбор типа вместо двух потенциально противоречивых классификаторов.
- Добавлены отдельные пустые состояния для нового реестра, отсутствующих результатов поиска и пользователя без доступных записей.
- Кабинет открывается как единое рабочее место с вкладками «Обзор», «Эталон», «Текущее», «Имущество», «Обход», «Vision», «Инциденты» и «История». В одной хронологии объединяются действия реестра, физические обходы, отчёты Agent и фотопроверки Vision; из шапки карточки администратор может изменить ответственного и сразу запустить Vision с уже выбранным кабинетом.
- Добавлен физический обход кабинета: сотрудник с правом редактирования обязан отметить каждую позицию как «на месте», «отсутствует» или «повреждено», указать число проблемных единиц и комментарий. Завершённый акт сохраняет исполнителя, серверное время и все результаты без перезаписи предыдущих обходов.
- Отсутствующая или повреждённая позиция автоматически создаёт физический инцидент. Во вкладке кабинета «Инциденты» ADMIN/EDITOR фиксирует обязательную причину и выбирает дополнительную проверку, перемещение, ремонт, списание либо ложное расхождение; решение сохраняется в истории актива.
- Для перемещения мастер запрашивает новый кабинет, количество и номер акта. При частичном переносе групповой позиции появляется поле нового инвентарного номера. Для списания мастер запрашивает количество и номер акта. После выполнения карточка кабинета обновляется, а закрытый инцидент предлагает скачать PDF-акт.
- Правило скрытия элементов унифицировано; проверена адаптивная ширина от 360 до 1842 px.

## Что остаётся проверить или реализовать

- Провести модерируемую проверку сценариев с администратором школы, инвентаризатором и IT-специалистом.
- Добавить сопоставление колонок для нестандартных Excel/PDF, явный список ошибок и объединение дубликатов до применения. Сейчас поддерживаются распознаваемые заголовки/типовая ведомость; повторный инвентарный номер сверяется внутри организации.
- Заменить оставшиеся браузерные запросы при редактировании карточки и решении инцидента на управляемые формы.
- Добавить ясную обратную связь для пустой структуры, недоступного сервиса и восстановления сессии.
- Проверить разрешения по ролям на реальном сценарии школы: пользователь должен видеть не только подходящий экран, но и только назначенные ему данные.

## Доступ по организации и локациям

- `ADMIN` видит всю доступную организацию; именованные пользователи привязаны к своей организации.
- Доступ ответственного определяется назначением `VIEWER` (просмотр) или `EDITOR` (просмотр и правка) на корпус, этаж или кабинет. Роль `LOCATION_MANAGER`/`INVENTORY_CLERK` обозначает рабочую функцию; сама по себе она не заменяет назначение области и разрешения.
- Ограничения проверяются API для реестра, карточек, отчётов, истории инвентаризации и связанных Vision-проверок; скрытие пункта интерфейса не является единственной защитой.
- Vision-комната связывается с кабинетом школьной иерархии. Однозначно сопоставленные старые комнаты мигрируются; неоднозначные записи остаются доступными только администраторам, пока их не свяжут вручную.
- Миграции `0020_expanded_user_roles` и `0021_vision_location_scope` добавляют поддерживаемые роли и связь Vision со структурой кабинетов. Полную матрицу проверок каждого admin endpoint, MFA/SSO и разделение ролей уровня школы/организации нужно завершить до multi-school production.

## Критерии приемки UX

- Новый администратор понимает первые шаги без устного объяснения.
- Поиск и открытие карточки доступны из реестра напрямую.
- Каждое сообщение «нет данных» объясняет причину или конкретное следующее действие.
- Вручную учитываемые предметы не помечаются как компьютеры без связи Agent.
- До применения импорта видно число новых и обновляемых записей; отмена не отправляет запрос на сохранение.
- Формы и навигация не создают горизонтальную прокрутку на ширине 360 px.
- Ответственный не получает доступ к чужим кабинетам ни через интерфейс, ни через API.
