# Приёмка интерфейса AssetGuard

Техническая проверка этапа 5 дополняет [ТЗ UI/UX](../product/ui-ux-modernization-spec.md). Она защищает критичные сценарии и измеряет известные ограничения; полный аудит WCAG и удобство работы сотрудника требуют отдельной ручной проверки.

## Автоматическая проверка

`backend/tests/e2e/test_ui_acceptance.py` использует существующий isolated PostgreSQL/live-server fixture и Chromium. Семь тестов проверяют:

- вычисленный контраст текста на однотонных поверхностях страницы входа и семи основных разделов; крупный текст ≥3:1, обычный ≥4.5:1, границы текстовых полей ≥3:1;
- подписи видимых полей и связь всех 11 диалогов с заголовками;
- отсутствие горизонтального растягивания страницы при ширине 320/360/390/768/1024/1366/1920 CSS px и в небольших viewport 640×400, 320×256;
- Tab/Shift+Tab, Enter/Space/Escape, видимую обводку, отсутствие перекрытия центра активного элемента, удержание фокуса в подтверждении и его восстановление;
- reduced motion и доступность короткого экрана: на нём навигация перестаёт занимать фиксированную область сверху;
- login → поиск → карточка → возврат → logout для ADMIN, VIEWER, LOCATION_MANAGER, INVENTORY_CLERK; две организации и отказы доступа к чужому активу/кабинету;
- 216 и 1000 synthetic assets: страницы по 20 строк, переходы, поиск и сохранение фильтра после карточки.

Запуск из `backend`:

```powershell
$env:ASSETGUARD_RUN_BROWSER_E2E = '1'
.\.venv\Scripts\python.exe -m pytest -q tests/e2e/test_ui_acceptance.py
Remove-Item Env:ASSETGUARD_RUN_BROWSER_E2E
```

Для диагностических файлов можно задать `ASSETGUARD_UI_PERFORMANCE_DIR`, `ASSETGUARD_UI_MEASUREMENT_REPORT`, `ASSETGUARD_UI_STAGE5_PREVIEW_DIR`. Пути отсчитываются от рабочего каталога. Создайте каталог для contrast report заранее. Скриншоты относятся только к синтетической тестовой БД; production screenshots и plaintext credentials в артефакты не сохраняются. Набор не отправляет Telegram и не подключается к production.

Измерение контраста учитывает прозрачность цветов и однотонные фоны предков, но не заменяет axe/ручной аудит: оно не проверяет все состояния, изображения/градиенты, SVG, pseudo-elements, групповой opacity и настоящее озвучивание экранным читателем. Проверка центра фокуса не доказывает полную видимость каждого пикселя обводки. Disabled controls исключены. Viewport 320 px проверяет reflow; он не является выполненной проверкой browser zoom 400%.

## Производительность

Cold workspace — время от нажатия «Войти» до готового реестра в новом browser context. Warm workspace — время обновления уже открытого реестра. Это включает HTTP чтение и отрисовку, но не является LCP. PerformanceObserver отдельно сохраняет document LCP (обычно страница входа), CLS, event durations и long tasks. Отсутствие events означает отсутствие записи длительностью ≥16 ms, а не нулевую задержку.

Локальный замер без CPU/network throttling — лабораторный smoke, не полевой INP/p75. Цели LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 остаются критериями для репрезентативных устройств и сетей. Тест не фиксирует нестабильное временное значение как CI threshold. Набор 1000 записей проверяет ограниченную отрисовку; backend пока возвращает весь список assets/endpoints, поэтому это не capacity acceptance нескольких школ.

`test_registry_query_budget.py` отдельно защищает производительность API: чтение 216 assets с двумя привязанными ПК сохраняет порядок, единственную строку на актив, название организации и правильную связь, выполняя ≤10 SELECT. Asset/endpoint/organization выбираются одним LEFT JOIN вместо endpoint lookup для каждой позиции. Уникальность `managed_endpoints.asset_id` обеспечена миграцией `0007`; tenant/location filters сохранены и проверяются отдельными тестами. Summary hardware пока читается отдельно для каждого привязанного ПК, а endpoints не имеют серверных страниц — эти ограничения ещё требуют оценки на большом парке.

## Ручная приёмка: ещё не проведена

1. В актуальных Chromium/Firefox проверить browser zoom 200% и 400%, в том числе короткий экран, формы, диалоги и локальные двумерные таблицы. Фиксировать браузер, разрешение, zoom и доступность основных действий.
2. Пройти вход, навигацию, формы/ошибки и диалоги с NVDA и клавиатурой; проверить порядок чтения, названия, объявления результата и возврат фокуса. Проверить мобильный браузер на настоящем устройстве.
3. Измерить representative performance на согласованном рабочем ПК и телефоне, холодной/тёплой загрузке и школьной сети. Сохранить параметры устройства/сети и выборку; не выдавать одиночный lab event duration за INP.

Для usability привлечь **3–5 представителей существующих ролей**. Использовать учебную организацию и обезличенные данные, отдельные учётные записи и реальные permissions. Участники выполняют применимые своей роли задачи: найти имущество и вернуться к фильтру; разобрать инцидент; провести обход и найти результат; проверить import preview; для ADMIN — найти stale PC/статус доставки и отменить отзыв ключа. VIEWER выполняет чтение и распознаёт недоступные операции.

Сначала участник работает без подсказки. Помощь отмечается отдельно и исключает задачу из «без подсказок»; не учитывать неприменимую роли задачу в знаменателе. Фиксировать анонимный код участника, роль, устройство, сценарий, время, результат, потребность в помощи, ошибку и краткое наблюдение. Цель: ≥90% применимых задач без помощи и отсутствие блокирующей ошибки/опасного действия. Сейчас это план, результаты и процент успеха не заявлены.

## Основания критериев

- [WCAG: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).
- [WCAG: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [Focus Not Obscured Minimum](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).
- [Web Vitals](https://web.dev/articles/vitals): различие лабораторных измерений и полевых результатов.
