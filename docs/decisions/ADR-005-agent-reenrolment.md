# ADR-005: Подтверждаемое восстановление Agent по SMBIOS UUID

- **Статус:** Accepted
- **Дата:** 2026-09-27

## Контекст

После переустановки Windows локальный Agent теряет credential, но AssetGuard должен продолжить историю прежнего endpoint без ручного редактирования реестра. Автоматическая выдача нового секрета только по hardware identifier позволила бы злоумышленнику, узнавшему UUID, перехватить устройство. Ручное создание и перенос credential безопаснее, но плохо масштабируется и провоцирует хранение секретов вне системы.

## Рассмотренные варианты

### Вариант 1: автоматическая выдача по SMBIOS UUID

Прост для оператора, но UUID не является секретом и не доказывает владение устройством. Вариант создаёт недопустимый риск захвата endpoint.

### Вариант 2: новый credential вручную для каждой переустановки

Не требует нового protocol, но заставляет администратора передавать секрет вручную, не обеспечивает единый lifecycle и повышает риск ошибки сопоставления.

### Вариант 3: короткоживущий claim с подтверждением администратора

Installer предъявляет UUID и случайный одноразовый token, администратор подтверждает запрос своей организации, после чего прежний активный credential отзывается, а token становится новым секретом.

## Решение

Использовать вариант 3. Запрос действует 30 минут. Публичное API всегда создаёт запрос и не сообщает, найден ли endpoint. Одобрить можно только запрос, заранее сопоставленный с активным endpoint по нормализованному SMBIOS UUID. Claim token остаётся в памяти installer; сервер хранит только SHA-256 для поиска запроса и PBKDF2 hash для будущей HTTP Basic проверки. Все admin операции tenant-scoped.

В решение не входят перенос устройства между организациями, полностью автоматическое одобрение, восстановление по имени компьютера и замена hardware identity.

## Обоснование

Схема сохраняет self-service на целевом ПК, но оставляет security-sensitive ротацию под контролем администратора. Она повторно использует существующие per-Agent credentials и hardware identity, не добавляет отдельный секрет-хранилище или внешнюю инфраструктуру.

## Последствия

Переустановка больше не требует ручного изменения `HKLM`. Одобрение сохраняет endpoint и inventory history, а прежний credential сразу перестаёт работать. Для аудита сохраняются запрос, решение и отозванные credentials. Администратор должен быть доступен в пределах 30-минутного окна.

## Риски

- Ошибочное одобрение отзовёт рабочий credential; UI явно предупреждает об этом и показывает UUID/имя компьютера.
- Клонированный или нестабильный SMBIOS UUID не подходит для восстановления; неизвестный identifier нельзя подтвердить.
- До отключения legacy shared secret он остаётся альтернативным путём ingest и должен быть удалён до массового multi-school rollout.
- Claim token находится в памяти PowerShell процесса во время ожидания; целевой ПК должен оставаться под административным контролем.

## Дальнейшая работа

Проверить flow после чистой переустановки на 3–5 пилотных ПК, добавить единый admin audit log, отключить legacy shared credential и включить управляемое обновление/rollback Agent. При появлении TPM/device certificates пересмотреть hardware identity как единственное основание сопоставления.
