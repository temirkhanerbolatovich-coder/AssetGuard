# ADR-007: Telegram через транзакционную очередь PostgreSQL

Status: Accepted. Date: 2026-10-05.

## Context

Пользователю нужны сообщения о новых инцидентах вместе с существующими проблемами Agent/сервера. Нельзя терять событие при сетевом отказе, задерживать ingestion Telegram request или раскрывать данные другого tenant. Production работает на Oracle Free VM с 1 GB RAM.

## Options considered

1. Отправка в HTTP transaction: проста, но связывает доступность Telegram с ingestion; откат после отправки создаёт ложное событие.
2. Опрос всей истории инцидентов: отдельный cursor и риск исторической массовой рассылки/неполной фиксации событий.
3. PostgreSQL outbox + короткий worker: текущая БД гарантирует атомарность; не требуется Redis/Celery или новый постоянно работающий container.

## Decision and reasoning

Добавлять ограниченный payload в таблицу очереди в транзакции создания инцидента. Выбирать due записи явно назначенной организации через `SKIP LOCKED`. Подтверждать `SENT` после положительного ответа Telegram с ожидаемым chat ID. Запускать короткий worker через существующий Linux/systemd deployment раз в минуту. Существующий health monitor отвечает за сводные эксплуатационные проблемы.

## Consequences and risks

Сохраняются retry/restart и уникальность source events; внешний сервис не влияет на успешность доменной записи. Network request держит только блокировку одной строки очереди и одно подключение БД до 10 секунд. Объём за запуск ограничен, поэтому при всплеске сообщений возрастает задержка. Гарантия at-least-once допускает дубль после acceptance-before-commit crash. В PostgreSQL сохраняются чувствительные описания имущества, retention пока ручной. Downgrade удаляет очередь и требует предварительной копии.

## Future work

Утвердить retention, административный просмотр/повтор, индивидуальные Agent state events и маршрутизацию нескольких tenant. Отдельный queue service оправдан при измеренном росте нагрузки, а не заранее. [Настройка, тестирование и ограничения](../features/telegram-notifications.md).
